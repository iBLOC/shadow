## 设计取舍

### DTLS 真 key export

之前 `shadow_dtls_derive_srtp_master` 是 folding-hash 占位(注释里 v2.2.1 替换)。现在 `shadow_dtls_handshake` 在 handshake 成功之后,直接调用:

```c
ret = mbedtls_ssl_export_keying_material(&ssl,
                                         "EXTRACTOR-dtls_srtp",
                                         NULL, 0,
                                         out_master_buf,
                                         SHADOW_DTLS_MASTER_BUF_LEN);
```

按 RFC 5764 §4.2,前 16 字节 = client_write_key,后 14 字节 = client_write_salt。30 字节正好是 `shadow_srtp_open` 期待的格式。

`shadow_dtls_derive_srtp_master` helper 保留(公共 API 仍可用),但是 v2.2.1 走了 live SSL context 的路径。

### STUN 简化实现

v2.2.1 写了最简 STUN 客户端:
- `shadow_stun_parse_binding_request`: 20-byte header 解析 + magic cookie check + 复制 tx_id
- `shadow_stun_build_binding_response`: 20-byte header + 13-byte XOR-MAPPED-ADDRESS + 8-byte FINGERPRINT
- CRC-32 用 Castagnoli 多项式查表 + mutex
- **FINGERPRINT 不参与自身 CRC** — 这是 RFC 5389 §6 行为,client/server 都要这样

## 已知边界

1. **没听 socket** — `stun.c` 只做 byte 协议,实际 UDP 监听在 dialog_task 实现
2. **没校验请求的 FINGERPRINT** — 我们信任 temporal lobe 的请求(controlled agent),不验证;严格模式要加
3. **没做 TURN 中继** — 家庭 Wi-Fi 应该够,复杂 NAT 留 v2.3
4. **没做 Trickle-ICE 增量 push** — 仍是一次性 push candidate list
