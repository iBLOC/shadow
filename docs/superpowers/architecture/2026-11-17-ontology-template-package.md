# 模板包 —— 「用户自己定义本体」的那一半

> 2026-11-17 ｜ 承 [通用化第一刀](2026-11-17-ontology-generic-ingest.md)（一张表 ⇒ 实体与关系）｜
> 本篇记**用户诉求的原文**、**三层模板的口径**、**这一刀落在哪**、**通用性怎么继续可判**，以及**仍然欠着的**。

---

## 1. 用户的诉求（逐字）

> 「我这个人力资源场景只是举个例子还可能有客户关系管理场景等等我在想这本体是不是可以支持模板」
>
> 「人力资源的代码你没有做进去吧 这应该是灵活的支持用户自定义的 用户也可以在界面新建本体而不是预置进去的
> 模板可以暂时使用json 后期会增加一个本体模型市场暂时先不做」

⇒ ⇒ 这三条把边界划得很清楚：

| 诉求 | 口径 | 这一刀 |
|---|---|---|
| HR **只是例子**（还有 CRM 等） | 场景差异只落在**模板数据**里，代码不认识任何场景 | ✅ 已有负控闸（O9 ＋ O10） |
| **支持用户自定义** | 本体形状由用户自己声明 ⇒ 模板里带**骨架声明** | ✅ 模板包的 `ontology` 段 |
| **界面新建本体**（而不是预置） | 客户端要有一个「建本体」的界面 | ⚠️ **欠着**（客户端面未做） |
| **模板暂时用 JSON** | 模板是 JSON 文档 | ✅ 就是 JSON |
| **本体模型市场** | 后期的事 | ⛔ **明确不做**（写进「不做清单」） |

---

## 2. 三层模板的口径（哪层落了、哪层欠着）

| 层 | 是什么 | 状态 |
|---|---|---|
| ① **摄取模板** | 表 → 实体与关系的映射（列名 ↔ 属性／关系名、键列、目标类） | ✅ 上一刀（`ImportTemplate`） |
| ② **本体骨架** | 类／关系类型／属性类型那一套（用户写的**本体形状**） | ✅ **这一刀**（`SchemaTemplate` ＋ 模板包的 `ontology` 段） |
| ③ **模板的生命周期** | 入库、版本、试运行、复用 | ✅ **这一刀**（存／取／列／版本不可变／dry-run） |

⇒ ⇒ 三层齐了 ⇒ ⇒ 「换场景只换一份 JSON」这句话**现在有实体**。

---

## 3. 落了什么

### core（`hippocampus-core/src/ontology/template.rs`）

- `TemplatePackage { id, version, ontology?, tables[], glossary }`
- `SchemaTemplate { classes[], relation_types[], attribute_types[] }`（骨架 ⇒ `OntologySchema`，出处 `Imported`）
- `TableTemplate { table, template }`（**多表** ⇒ 一份包管多张表）
- 存储面：`save_template` / `load_template` / `list_templates`
  —— 模板存在**租户自己的本体图**里（类 `模板`，实体 id `模板:{id}@{version}`）
  ⇒ ⇒ 租户隔离天然成立；**版本并存**；**同版本不可改**（内容不同 ⇒ 报错 ⇒ 要改就升版本号）
- `dry_run_package`：**不落库**，报「会写多少／会跳过多少／哪些关系接不上」
- `ingest_package_into`：**先声明骨架、后摄取**（同优先级 ⇒ 先来的赢 ⇒ 声明的父类／说明**保住**）
- ⚠️ 冲突分析抽成**纯函数** `plan_writes`（在 `ingest.rs`）⇒ ⇒ 试运行与正式摄取**共用同一处判读**
  ⇒ ⇒ 「试运行说写 N 条、真跑写了 M 条」这件事**不可能发生**

### server（`hippocampus-server`）

| 路由 | 干什么 |
|---|---|
| `POST /api/ontology/{tenant}/templates` | 存模板包（JSON 进） |
| `GET /api/ontology/{tenant}/templates` | 列模板（每个 id 一条最新） |
| `GET /api/ontology/{tenant}/templates/{id}` | 取模板（`?version=N` 取指定版本） |
| `POST /api/ontology/{tenant}/templates/{id}/dry-run` | 试运行（**不落库**） |
| `POST /api/ontology/{tenant}/templates/{id}/ingest` | 按包摄取多张表 |

⇒ ⇒ 人格仍在路径里 ⇒ ⇒ 租户隔离沿用 `TENANT_PATH_COLLECTIONS`（`"ontology"` 已在里面）⇒ ⇒ 不用改。

### 父仓闸（`scripts/check-ontology-network.mjs`）

- **第十条判据 O10「模板面」**：模板包三件套 ＋ 入库三个函数 ＋ 试运行 ＋ 服务端五条 handler ＋ 四条路由
  ＋ **共用判读**（`plan_writes` 定义在 `ingest.rs`、调用在 `template.rs`）
- ⚠️ **负控词表扩到 CRM 族**（客户／联系人／线索／阶段／渠道／合同／订单）
  ⇒ ⇒ **词表必须随场景扩** ⇒ ⇒ 不然这道闸会把「HR 通用」当成「通用」（那是尺子自己骗自己）
- 自检 **13/13**（O10 两道变异：模板面缺了 ／ 场景词漏进了模板面）

## 4. 模板包的形状（**场景无关**的骨架 ＋ 例子）

```json
{
  "id": "books",
  "version": 3,
  "ontology": {
    "classes": [
      { "id": "书目", "label": "书目", "description": "一本被记录下来的东西", "parent": null },
      { "id": "作者", "parent": "书目" }
    ],
    "relationTypes": [
      { "id": "著有", "domain": "作者", "range": "书目" }
    ],
    "attributeTypes": [
      { "id": "页数", "datatype": "number" }
    ]
  },
  "tables": [
    { "table": "作品表", "template": {
        "class": "书目", "keyColumn": "编号",
        "attributes": [ { "column": "标题", "name": "标题" } ],
        "relations": [ { "column": "作者编号", "name": "著有", "targetClass": "作者" } ] } },
    { "table": "作者表", "template": {
        "class": "作者", "keyColumn": "编号",
        "attributes": [ { "column": "笔名", "name": "笔名" } ] } }
  ],
  "glossary": { "页数": "口径：含附录" }
}
```

⇒ ⇒ **同一个骨架，换一份 JSON 就是另一个场景** ⇒ ⇒ 代码一行不动。

### 四条语义纪律

1. **版本不可变**：同 id 同版本内容不同 ⇒ **报错**（要改就升版本号）⇒ ⇒ 老版本永远读得回来。
2. **先声明骨架、后摄取**：同优先级下**先来的赢** ⇒ ⇒ 声明的父类／说明**保住**；顺序反了就会被推断的那条压住。
3. **试运行不落库**：数字来自**同一个**冲突分析函数 ⇒ ⇒ 与真跑一致。
4. **口径跟着模板走**：`glossary` 是模板的一部分 ⇒ ⇒ 「同一个词在不同口径下含义不同」这件事有地方放了。

## 5. 通用性怎么继续**可判**

- 闸扫的是**实现段**（去掉注释、去掉 `#[cfg(test)]` 之后）⇒ ⇒ 文档与测试里可以出现场景词，**代码里不行**。
- 场景词现在覆盖 **HR ＋ CRM** 两族 ⇒ ⇒ 下一族场景来了，**先加词表**，再加模板。
- 两道真变异（合成夹具）：模板面缺了 ／ 场景词漏进模板面 ⇒ ⇒ 各**恰好红一条**。

---

## 6. 路线图与欠账

### 这一刀欠着的

- ⚠️ **客户端「界面新建本体」没有做** ⇒ ⇒ 用户在界面上还**看不到**本体编辑器 ⇒ ⇒
  本体现在只能靠**手写 JSON** 起步（客户端面是下一层：模板编辑器 ＋ 骨架编辑器）。
- ⚠️ **真文件上的真变异还没做**（O9／O10 的变异都跑在合成夹具上）。
- ⚠️ **真二进制那一格仍空**（e2e 走的是进程内 router ⇒ 「进程重启后三元组仍能读回」未验）。
- ⚠️ **真机那一格仍空**。

### 明确**不做**的

- ⛔ **本体模型市场**（用户明确说后期再说）⇒ ⇒ 这一刀**不预置任何场景模板**（HR 的、CRM 的都没有）
  ⇒ ⇒ 模板永远是**用户自己的数据**。

### 下一刀该补的（按顺序）

1. **xlsx 二进制解析**（文件 → 表）⇒ ⇒ 上一刀的摄取器吃的是「表」，就差这一步 ⇒ ⇒
   「发个 Excel 就建本体」那条路才真通。
2. **客户端界面新建本体**（模板编辑器 ＋ 骨架编辑器）⇒ ⇒ 用户不用手写 JSON。
3. **事件流／多值属性／身份合并**（这一族场景才有的建模需求）⇒ ⇒
   现在的属性是**单值**（后写覆盖）、实体 id 是 `类:键`（跨源同名就是两个实体）。

---

## 7. 一句话口径

> **本体＝应用** ⇒ ⇒ 应用的**形状**由用户自己写（模板包 ＋ 骨架），
> 应用的**行为**由平台提供（摄取 ＋ 查询 ＋ 报告）⇒ ⇒ 换场景只换数据，不换代码。
