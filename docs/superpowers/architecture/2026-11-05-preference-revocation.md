# 「用户偏好撤销通道」—— 把 authority lapse 变成会红的判据

> 2026-11-05 ｜ 依据 arXiv:2606.30306《Always-On Agents》§2.5 与 §9.6
> 落地件：scripts/check-preference-revocation.mjs ／ scripts/lib/preference-revocation.mjs ／ state/revocation-ledger.json

---

## 一、为什么要有这条通道

论文那篇用 **435 项工作的编码**量过一个形状：retrieve **269** / write **200**，
但 audit **88** / forget **66** / **rollback 27**；六轴里 **authority 只有 72**
—— 最稀有的一轴。它在 §2.5 点名的失败叫 **authority lapse**：

> 用户说了一个偏好，后来撤回，agent 仍照做。

「遵循一个**已说出的**偏好」和「尊重一个**被撤销的**偏好」是两件事，
而绝大多数评测只测前者。

我们本机今天的样子**一模一样**（实测，不是推测）：

| 项 | 实测 |
|---|---|
| 用户记忆面（user.md） | **1 条**偏好（自主推进偏好） |
| 撤销通道 | **0 条** —— 偏好一旦说出口，只能靠人肉记住它被撤过 |
| 撤销记录 | **不存在** |
| 「撤回后是否仍生效」的可判定性 | **无** |

而我们最强的另一半（三十多道 check-* 静态闸，带自检 ＋ 退化副本反向验证）
**全建在源码上** —— 状态面那一条线，本条是第二道。

---

## 二、三件套

### ① 撤销账本（deletion ledger）

论文 §9.6 的 required ablation 点名要一个 **deletion ledger**。
我们落成仓内一份只追加的机器可读账本：**state/revocation-ledger.json**。

每条记录一次撤回，带全六字段信封（复用状态面闸的同一套字段与合法值集合）：

    epoch / authority / scope / source / status / supersedes

外加「id」（rev-XXXX）、「target」（撤的是哪条偏好）、「action」（revoke / restore）、「reason」。

### ② 撤回声明（注入面里看得见的形状）

用户记忆面里追加一条**独立条目**：

    ### 撤回声明：偏好名（2026-11-05，rev-0001）
    > 信封：epoch=2026-11-05 | authority=user | scope=user | source=撤销账本 rev-0001 | status=active | supersedes=none

    偏好「偏好名」已于 2026-11-05 被撤回（rev-0001）⇒ ⇒ **上文那条关于它的描述作废，不得再作为偏好执行**。

另一种形态也认：偏好条目自己带「—— 已撤回（日期，rev-id）」后缀。
两种都认 ⇒ ⇒ 将来运行时支持原地改写时，不必改判据。

### ③ 闸（会红的代码，不是文档）

scripts/check-preference-revocation.mjs —— 七条判据，纯函数在
scripts/lib/preference-revocation.mjs。

## 三、协议：三步撤销流程（可执行）

当用户说「这条偏好取消」「以后别按那个来」时：

    ① 写撤销账本条目
       state/revocation-ledger.json 里追加一条：
       { id: "rev-0002", target: { surface: "user-memory", key: "<偏好名>" },
         action: "revoke", epoch: "<今天>", authority: "user", scope: "user",
         source: "<用户原话摘要>", status: "active", supersedes: "none",
         reason: "<为什么撤>" }

    ② 在用户记忆面追加一条撤回声明
       用记忆工具 append（**只支持 append**，见第五节），标题形状：
       ### 撤回声明：<偏好名>（<今天>，rev-0002）

    ③ 跑闸，必须绿
       node scripts/check-preference-revocation.mjs --include-local

    ④ 传播（如果别的面也提了这条偏好）
       派生副本的**条目标题**里必须带上 rev-0002，否则 V6 会红。

**账本只追加**：撤销记录不许被抹掉。要恢复，就另写一条 action=restore 的条目，
不许删掉原来那条 revoke。

## 四、判据七条

| 规则 | 守什么 | 失败时人看到的话 |
|---|---|---|
| **V1** | 账本信封齐全、值合法、取代链可解析 | 「撤销账本 rev-0001：信封缺字段 source ⇒ ⇒ 这次撤销没有完整的授权/来源 ⇒ ⇒ 不可审计」 |
| **V2** | **只有用户本人**能撤回用户偏好 | 「authority 是「measured」⇒ ⇒ 只有用户本人能撤回用户偏好（论文 §2.5 authority）」 |
| **V3** | 目标指得准（偏好不得重复、不得指向不存在的东西） | 「目标偏好「X」在用户记忆面里**既没有条目也没有撤回声明** ⇒ ⇒ 这次撤销是空的」 |
| **V4** ★ | **撤了必须真的生效**（防 authority lapse） | 「用户撤了偏好「X」（rev-0001）⇒ ⇒ 但偏好面里它**仍是生效形态** ⇒ ⇒ 这就是论文说的 **authority lapse**」 |
| **V5** ★ | **生效的撤销必须有来源**（防幽灵撤销） | 「撤回声明「X」（rev-0001）⇒ ⇒ 但撤销账本里**没有** rev-0001 ⇒ ⇒ 这次撤销没有来源（论文：a memory that drops its source ⇒ ⇒ strictly worse than empty）」 |
| **V6** | **派生副本必须传播** | 「被撤回的偏好「X」在派生面「agent-memory」的条目里仍然**照旧生效** ⇒ ⇒ 未来会话读到它仍会照做」 |
| **V7** | rev-id 不许重复、restore 必须配对 revoke、恢复后不许还挂着撤销标记 | 「撤销账本里 rev-0001 出现了 **2 次** ⇒ ⇒ 撤销标记会指错」 |

**判据认形状不认关键词**（与本仓既有判据同源）：

- 撤回的形状是**标题行**的「撤回声明：…（日期，rev-id）」或条目末尾的「—— 已撤回（…）」；
- 正文里提一句「已撤回」**不算**撤回（否则「正文提一句」就能把一条仍然生效的偏好喂绿）；
- 派生副本的形状是**标题里带 rev-id**，正文提及不算。

## 五、⚠️ 实测约束：运行时对用户偏好**只支持 append**

2026-11-05 实测记忆工具对 user 面的操作支持情况：

| 操作 | 结果 |
|---|---|
| read / search / append | ✅ 可用 |
| **edit** | ❌ INVALID_OPERATION |
| **write** | ❌ INVALID_OPERATION |

⇒ ⇒ **原条目改不掉** ⇒ ⇒ 撤销只能表达成「追加一条撤回声明」。

这带来一个**必须说清楚的残余风险**：

> 撤回声明在文件里，原条目也还在文件里。
> 「模型读到撤回声明之后就不照做」**不是机械保证**，是模型遵守约定。
> 闸能证明的是「撤回声明存在、且与账本一致、且派生副本已传播」，
> **证明不了**「模型一定不照做原条目」。

⇒ ⇒ 那一环只能靠**真机行为测试**（派一个全新会话问它偏好列表），
而且它**必须被当作独立的验证级别**记在读数里，不能被「闸绿」替代。

## 六、验证阶梯（四级，逐级递进，别用低级别冒充高级别）

| 级别 | 手段 | 判什么 |
|---|---|---|
| **编译级** | node scripts/check-preference-revocation.mjs --self-test | 判据本身对不对：21 条逐条退化 ＋ 孪生 ＋ 完整生命周期演练 |
| **承载级** | node scripts/check-preference-revocation.mjs --drill | 机制通不通：在**副本**上走完整条链，每一步该红的地方都红；真文件 SHA256 前后逐字一致 |
| **真机级** | 在**真实** user.md 上写账本 → 跑闸看它红 → 追加撤回声明 → 跑闸看它绿 | 真实面上判据真的会红、真的会绿 |
| **真机级++** | 派一个**全新会话**问它「哪些用户偏好在生效」 | 模型读到撤回声明后**会不会照做**（第五节说的那一环） |
| **回归级** | 状态面闸 self-test ＋ 主检查（两道） | 新闸没有把旧闸带崩（共享判据库改过） |

**反向验证纪律**：退化只发生在**内存副本**里，真文件一个字不动；
跑完核对 SHA256 逐字未变。

---

## 七、覆盖边界（如实标注）

**判得了**：撤销记了没有、生效了没有、来源在不在、派生副本传播了没有、
谁授权的、目标指得准不准。

**判不了**：

1. 模型读到撤回声明后**是否真的不照做**（模型约定，不是机械强制）；
2. **跨设备**同步来的撤销记录（本机闸看不见别的设备写进来的那一份）；
3. 用户记忆面在 **CI 里不存在** ⇒ ⇒ V3/V4/V5/V6 那几条在 CI 上**明确报「本轮未覆盖」**，
   不假装绿（CI 守的是账本自身 V1/V2/V7 ＋ 自检里的完整生命周期演练）；
4. 派生副本的**正文**里提到被撤偏好（只认标题形状）。

**仍然欠着**：

- 运行时**不支持** user 面的 edit/write ⇒ ⇒ 原条目永远留在文件里；
  要真正物理删除，需要运行时给记忆子系统加 delete/update（产品侧改动，不在本仓范围）；
- 「delete」能力**本轮未探测**（怕误删真实记忆 ⇒ ⇒ 宁可欠着，不拿真实偏好做赌注）；
- 跨设备同步来的撤销记录没有判据；
- 跨面撤销（父仓撤了，子仓的副本怎么办）只有 V6 的标题级传播，没有语义；
- **agent 记忆层「悬空引用」这条债会单调增长**（1 → 4，2026-11-05 实测）：
  记忆层每次提到账本条目就顺手抄它的带圈编号，而记忆层**没有编号体系**
  ⇒ ⇒ 靠登记堵不住 ⇒ ⇒ 真解是禁止在记忆层用带圈引用。
